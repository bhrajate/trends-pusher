# 每日推送时间设计

> 为什么要错开推送，以及每个时间点背后的考量。

---

## 设计目标

**避免信息轰炸** — 5 个数据源如果在同一时段集中推送，用户的飞书/微信会被连刷 5 条消息，体验很差。

将推送均匀分布在全天，每次只推送 1 条，间隔至少 2 小时，让用户在每个时段自然地接收合适的内容。

---

## 推送节奏一览

```
09:00   🔥 GitHub Trending
             │
12:00   ⛏️ 稀土掘金
             │
14:00   💻 牛客
             │
16:00   🦄 Product Hunt
             │
18:00   🔶 Hacker News
```

| 北京时间 | 数据源 | 间隔 | 使用场景 |
|----------|--------|------|---------|
| 09:00 | 🔥 GitHub Trending | — | 早上开工前，扫一眼昨天 GitHub 热门项目 |
| 12:00 | ⛏️ 稀土掘金 | 3h | 午饭时间，刷中文技术文章 |
| 14:00 | 💻 牛客 | 2h | 下午开工，看看面试题和职场讨论 |
| 16:00 | 🦄 Product Hunt | 2h | 下午茶歇，PH 日更刚出炉（PT 午夜 ≈ 北京 15:00） |
| 18:00 | 🔶 Hacker News | 2h | 下班通勤 / 晚间时段，适合深度阅读技术新闻 |

## 为什么不合并成一条消息？

| 合并 | 分开 |
|------|------|
| 5 个源混在一起，信息量大难以消化 | 每个源独立，内容聚焦 |
| "早上 10 点看一眼就没了" — 全天无期待 | 全天多个时间点都有新鲜感 |
| 不同源的内容特征差异大，混排不协调 | 每个时段输出内容类型匹配当前场景 |

## 各数据源的分析

### 🔥 GitHub Trending — 09:00

- **内容类型**：开源项目列表（项目名 + 描述 + Star 数）
- **适合时段**：清晨或早上
- **理由**：GitHub Trending 的日榜在每天刷新后内容相对稳定，早上推送可以让用户在开始一天工作前快速扫读昨晚的热门开源项目，作为一天的技术灵感来源
- **代码场景**：很适合在工位上打开电脑后收到，点进去 star 或 clone

### ⛏️ 稀土掘金 — 12:00

- **内容类型**：中文技术文章、教程、经验分享（适合快速扫读）
- **适合时段**：午饭时间
- **理由**：稀土掘金以中文前端 / 全栈文章为主，文章长度适中，很适合午饭时边吃边看。这个时间点也是内容被社区筛选了一上午、"真正好的文章"逐渐浮现的时候

### 💻 牛客 — 14:00

- **内容类型**：面试题讨论、职场交流、校招/社招动态
- **适合时段**：下午开工
- **理由**：下午刚开始工作，推送一些轻松的面试讨论和职场话题作为调剂。牛客的内容偏向求职成长，不太需要深度阅读，适合工作间隙扫一眼

### 🦄 Product Hunt — 16:00

- **内容类型**：新产品发布、Maker 社区推荐
- **适合时段**：下午茶歇
- **理由**：Product Hunt 的每日榜单在太平洋时间午夜刷新（对应北京时间 15:00），16:00 推送时榜单上的产品已经积累了第一波投票和评论，数据更有参考价值。新产品内容轻松有趣，适合下午精力低谷时浏览

### 🔶 Hacker News — 18:00

- **内容类型**：深度技术新闻、行业讨论、学术论文链接
- **适合时段**：晚间
- **理由**：Hacker News 是 5 个源中内容最"硬核"的——通常是长文章、论文、技术博客。这类内容需要沉浸式阅读，不适合工作时间碎片化消费。18:00 推送，用户可以下班通勤时或晚间在家静下心来看

## Cron 配置表

| Workflow 文件 | cron (UTC) | 北京时间 |
|--------------|------------|---------|
| `push-github.yml` | `0 1 * * *` | 09:00 |
| `push-juejin.yml` | `0 4 * * *` | 12:00 |
| `push-nowcoder.yml` | `0 6 * * *` | 14:00 |
| `push-producthunt.yml` | `0 8 * * *` | 16:00 |
| `push-hackernews.yml` | `0 10 * * *` | 18:00 |

> 北京时间 = UTC + 8。GitHub Actions 的 `schedule` cron 使用 UTC 时间。

---

## 例外处理

- 所有 workflow 均支持 `workflow_dispatch` **手动触发**，不受 cron 限制
- GitHub Actions 的 scheduled workflow **不保证准时执行**，高峰时段可能有数分钟到数十分钟的延迟，但相对顺序会维持
- 如果某天某个源没有新内容（不常见），对应 workflow 会自动跳过（空列表则 exit 0）
